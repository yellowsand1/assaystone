The transcript is not the filesystem

How to audit a Codex or Claude Code session in one command — and where that audit goes blind.

ASSAYSTONE 0.5.0TWO TRANSCRIPT FORMATS88 TESTS PASSINGNO MODEL CALLS
1command to audit the newest local session
2transcript formats normalized into one trace
88tests passing on the 0.5.0 repository
0API keys or uploads required
Assaystone 0.5.0 can audit the newest local Claude Code or Codex CLI session with one command. This post explains the implementation rather than the pitch: how two different transcript formats are normalized, how Codex apply_patch edits are replayed onto a baseline, how the latest session is discovered, why a log of tool calls is not the same thing as the filesystem, and exactly where path-based test-integrity checks and arbitrary shell writes go blind. It includes runnable commands, real output from the bundled demo, and the test evidence behind the claims.

“Your agent's tests pass. Did it delete the failing test?”

It sounds like an accusation. Most of the time it is not one. In a corpus of 162 real Claude Code sessions, 28 sessions touched test files, and 27 of those also touched source files. That is ordinary feature work: implementation and tests move together.

But the question points at a real gap. A green suite proves that the tests which ran passed. It does not prove that the test which mattered still exists, that the agent changed only what it said it changed, or that “all tests pass” was supported by anything the session actually recorded.

Assaystone 0.5.0 turns that question into a command:

pip install assaystone==0.5.0
assaystone audit --latest claude-code   # or: --latest codex

It finds the newest local transcript for the current workspace, reconstructs the files the session touched, runs a default contract, and prints findings plus a suggested contract. No API key, no hosted control plane, no upload. Exit codes are 0 clean, 1 findings, 2 the input could not be audited.

The bundled failure case is the fastest way to see the shape of the output:

python3 -m assaystone demo audit
Assaystone audit demo — a coding-agent transcript
Assaystone audit
baseline: demo transcript
traces: 1 (0 clean, 1 with findings)

audit-demo-session  changed: pricing/discounts.py, tests/test_discounts.py
  HIGH     tests.integrity          tests/test_discounts.py (modified)

summary: 0 critical, 1 high, 0 medium, 0 low

suggested contract: assaystone-demo-contract.json

details: assaystone-demo-audit.md

The demo agent fixed a rounding bug, deleted the one test it still failed, and reported success. A conventional test run saw a green suite. The audit saw the deleted test because it reconstructed the file changes instead of trusting the final message.

That reconstruction is the interesting engineering. It is also where the limits live.

1. What the audit actually does

The pipeline has three stages.

StageCodeWhat it produces
Discoverassaystone/sessions.pyThe newest transcript whose recorded working directory contains the current directory
Reconstructassaystone/audit.py, assaystone/replay.pyA Trace with steps, tool results, and changed-file artifacts
Verifyassaystone/verifiers.py, assaystone/runner.pyFindings from a default contract, plus a suggested contract

The audit is deliberately usable before you have a contract. build_audit_contract() in assaystone/audit.py scaffolds one from the repository, drops tests.pass unless you pass --run-tests, raises the step budget to 5,000, sets diff.max_lines to 400, and runs with fail_fast=false so every finding is reported rather than only the first.

It never edits the repository. The only writes are explicit output files (--write-contract, --sarif, --junit) and the Stop hook's local dedupe cache.

2. A transcript records intentions, not files

Claude Code and Codex CLI write different JSONL shapes.

Claude Code entries look like this:

{"type": "assistant", "sessionId": "abc", "message": {"role": "assistant", "content": [
  {"type": "text", "text": "I'll inspect the tests."},
  {"type": "tool_use", "id": "t1", "name": "Read", "input": {"file_path": "tests/test_x.py"}}
]}}

Tool results come back as user entries with tool_result blocks. Codex writes a session_meta record followed by response_item records: message, function_call, and function_call_output, with the tool name and JSON-encoded arguments on the call.

The loader detects the shape rather than trusting the file extension. _looks_like_claude_code() checks for type: user|assistant entries with a message; _looks_like_codex() checks for session_meta or response_item function calls. _normalize_claude_code() and _normalize_codex() convert both into a common message list, and from_messages() in assaystone/adapters/messages.py pairs each call with its result by call_id, producing a Trace of ordered Steps.

That gives you a clean log. It does not give you the files.

3. Why recording only tool calls is not enough

A tool-call log is a record of what the harness says the agent asked for. It is not the filesystem. The difference is large enough that it changes the product.

In the 162-session field audit behind the published field note:

SignalNumber
Usable sessions162 (from 167 JSONL files, roughly 578 MB)
Recorded agent steps28,082
Steps that were Bash commands20,688, about 74%
Sessions that wrote files through shell commands61
Sessions with shell-only writes and no Edit/Write artifacts16
Sessions that wrote into test-like paths through the shell4

The shell patterns included cat >, tee, sed -i, patch, perl -pi, and git apply. If a verifier only understands editor tool calls, it misses most of what the agent actually did — not because the agent hid anything, but because the editor is not the only interface.

Assaystone 0.5.0 has three recovery paths, each with a different trust model:

  1. Transcript replay. Write sets content, Edit applies old_string → new_string (honoring replace_all), MultiEdit applies edits in order, and Codex apply_patch is parsed and applied. This is the default. It works without git, but it only sees tool calls it recognizes.
  2. --git-repo. artifacts_from_git() collects tracked changes against HEAD plus untracked, non-ignored files. This sees shell writes, but only inside a git repository, and only for paths git reports.
  3. Workspace mode plus a git working-tree merge. The Claude Code Stop hook reads the current files for touched paths (workspace_artifacts()). When the hook's cwd is the git root, it also merges artifacts_from_git(cwd) so sed, tee, and patch edits become visible to path, syntax, and diff checks.

The third path is why the 0.5.0 hook is more useful than transcript replay alone. It is also why the hook's blind spot is precise: if Claude Code was launched from a subdirectory of the repository, is_git_root(cwd) is false, and the merge does not happen. Run the hook from the repository root, or pass --git-repo/--git-preimage explicitly.

Test evidence is a separate inference problem. evidence.claims only fires when the final message contains a narrow success claim such as “all tests pass”, “tests are green”, or “tests look good”. It then looks for test_exit_code in the trace evidence. That value is inferred only when a step runs a recognized test runner — pytest, python -m pytest/unittest, npm test, pnpm/yarn test, npx jest/vitest, go test, cargo test, Maven/Gradle, jest, vitest, rspec, dotnet test, or ctest — and the output has an unambiguous outcome.

If the claim exists but no evidence was recorded, the verifier escalates rather than passing:

REVIEW   evidence.claims   agent claims tests pass but no test evidence was recorded

That is the right default. A verifier that guesses is worse than one that says it cannot decide.

4. How Codex apply_patch is reconstructed

Codex often does not call a dedicated apply_patch tool. It runs exec_command with a shell here-doc:

{
  "type": "function_call",
  "name": "exec_command",
  "arguments": "{\"cmd\": \"apply_patch <<'PATCH'\\n*** Begin Patch\\n*** Delete File: tests/test_calc.py\\n*** End Patch\\nPATCH\"}"
}

audit.py detects that shape in _normalize_codex(): if the tool is exec_command and the command contains a patch, _codex_patch() extracts everything from *** Begin Patch through *** End Patch, renames the step to apply_patch, and stores the patch text.

assaystone/replay.py then parses the patch into sections:

  • *** Add File: path
  • *** Update File: path
  • *** Delete File: path
  • *** Move to: path

_apply_patch_sections() applies them in order against a mutable view of the baseline:

  • Add takes body lines beginning with + (ignoring +++) as the new content.
  • Delete marks the path deleted.
  • Update loads the current text, splits the body on @@ hunk headers, collects - and context lines as the old block and + and context lines as the new block, and replaces the first exact occurrence.
  • Move writes the updated text to the destination and deletes the source.

Path handling is deliberately conservative. relative_path() rejects absolute paths outside the baseline and any path beginning with ... The test test_codex_patch_cannot_escape_the_baseline asserts that a patch adding ../escaped.py produces zero artifacts and does not create a file outside the workspace.

The tests also pin the two useful cases:

  • A patch deleting tests/test_calc.py produces one artifact with change type deleted, and the audit reports tests.integrity.
  • A patch updating an assertion reconstructs the file as def test_add():\n assert True\n.

The limits are equally concrete:

  • Update matching is exact block replacement. Whitespace drift or a stale context block means the update is skipped silently.
  • Line numbers and fuzzy context matching are not implemented.
  • Added-file content is taken only from + lines; binary files are not handled.
  • The patch must appear in the command string. If Codex changes its invocation wording, _codex_patch() returns None and the step stays an opaque exec_command.
  • The tests use synthetic JSONL written to the current record shape. They do not prove that a future Codex release will keep that shape.

5. Finding the newest session

assaystone/sessions.py is small and intentionally boring.

def find_latest_session(agent, *, cwd=".", root=None) -> SessionSource:
    ...
  • Default roots: ~/.claude/projects for Claude Code and ~/.codex/sessions for Codex.
  • Overrides: ASSAYSTONE_CLAUDE_ROOT and ASSAYSTONE_CODEX_ROOT.
  • Candidates: every *.jsonl under the root, recursively, sorted by file mtime descending.
  • Header scan: read up to 40 lines per file, parse JSON, and take payload.cwd (Codex) or cwd (Claude Code).
  • Match rule: the recorded session directory equals the requested directory, or the requested directory is inside it. That is _workspace_match(); it lets you run the command from src/package and still find a session started at the repository root.
  • Result: the first match, or SessionDiscoveryError, which the CLI turns into exit code 2.

assaystone audit --latest codex then sets the baseline to the session's recorded cwd (unless you pass --baseline), sets the format to the agent name, and enables --git-repo automatically when that baseline is a git repository. It prints the chosen transcript path to stderr:

latest codex session: /path/to/sessions/2026/11/24/session.jsonl

This is discovery, not indexing. It does not scan transcript bodies for keywords, does not read prompts, and does not upload anything. The trade-off is that “latest” means newest matching file by mtime, not the session with the newest turn. The 40-line header scan and the one-session-per-file layout are assumptions; if your tool stores sessions differently, pass an explicit path or set the root override.

6. What the default rules can and cannot say

The audit contract is code-centric. These are the defaults in assaystone/audit.py:

RuleSeverityWhat it actually checks
diff.syntaxcriticalast.parse() on changed .py files; deleted files are skipped
tests.integrityhighchanged paths under configured test prefixes
diff.forbidden_pathshighchanged paths matching protected CI/config paths
evidence.claimshighfinal-message success claim versus recorded test_exit_code
diff.public_apimediumremoved or changed public functions/classes
quality.no_debug_printsmediumprint() or breakpoint() in changed Python, excluding tests/examples/scripts
diff.max_lineslowmore than 400 changed lines in the audit contract
budget.stepslowmore than 5,000 steps

The protected test prefixes come from directories that exist in the repository: tests/, test/, and spec/, with tests/ as the fallback. _path_under() matches exact prefixes and nested occurrences, so server/tests/test_api.py is covered by tests/.

The honest part: tests.integrity is path-based

tests.integrity flags that a test file was modified or deleted. It does not know why. It cannot tell whether the agent protected the product or protected itself.

The field audit is the calibration for that sentence. Twenty-eight sessions touched test files. Twenty-seven also touched source. The one test-only session turned out to be a fixture and schema refactor during an upstream bug investigation. Manual review of the five strongest candidates — including four sessions that wrote into test-like paths through shell commands — found zero confirmed test tampering. One added new tests; three wrote temporary probe scripts or delivery notes whose contents happened to mention test paths.

The finding should be read as: test-directory activity happened; review it. Not: the agent cheated.

There is also a naming blind spot. _detect_protected() only detects tests/, test/, and spec/. A repository that keeps tests in __tests__/, or at the root as test_foo.py with no tests/ directory, will not be protected by the default contract. You can fix that with a custom contract's protected_prefixes, but the default does not guess.

diff.public_api has a similar proxy problem. Deleting a test module trips it, because the module's public symbols disappear. That is noise in a test-focused audit; the contract and the hook's ignore rules are where you tune it.

7. From audit to gate

The Stop hook is the daily-workflow version of the same audit.

assaystone hook install claude-code --mode warn

It merges the hook into .claude/settings.local.json for the project, or ~/.claude/settings.json with --user, and is idempotent. The installed command is assaystone hook claude-code.

The hook reads Claude Code's JSON payload from stdin: transcript_path, cwd, and stop_hook_active. It then:

  1. Audits the transcript in workspace mode.
  2. If cwd is the git root, merges working-tree changes so shell edits are visible.
  3. If the repository has a HEAD commit, builds a temporary pre-image from HEAD for the changed paths, so diff-size and public-API checks still have a baseline.
  4. Applies .assaystone/hook.json ignore rules.
  5. Prints a compact summary, or nothing if there are no findings.

Modes:

  • warn (default): exit 0; Claude stops normally.
  • block: exit 2 for findings at or above fail_on (default high); Claude sees the message and continues.
  • stop_hook_active: exit 0 to avoid a loop.
  • Audit failure: fail open with a message. A broken hook should not break the session.

The hook also dedupes the same finding within a session by hashing the message into a cache under XDG_CACHE_HOME/assaystone/hooks/.

There is a plugin path too:

/plugin marketplace add yellowsand1/assaystone
/plugin install assaystone@assaystone

The plugin adds /assaystone:audit, /assaystone:setup, and a Stop hook whose shell wrapper exits 0 if the assaystone CLI is missing. It fails open by design.

For CI, the same findings can be written as SARIF or JUnit:

assaystone audit agent-transcripts/ --baseline . \
  --sarif results.sarif --junit results.xml --fail-on high

The composite GitHub Action exposes verdict, findings, and traces outputs and runs assaystone verify against a contract.

8. Limits and blind spots

The list matters more than the feature list.

  • The transcript is not ground truth. Replay sees recognized tool names and argument shapes. Custom tools, renamed tools, truncated tool output, and arbitrary shell side effects can all be invisible.
  • Arbitrary shell writes need git. sed -i, tee, cat >, patch, and git apply are not reconstructed from the transcript. --git-repo or the hook's working-tree merge is what catches them. Writes to ignored files, files outside the repository, or committed changes can still fall through.
  • A commit changes the baseline. If the agent committed its own work, --git-preimage builds from HEAD, which is already post-session. Path rules still work; diff-size and public-API checks become less meaningful.
  • tests.integrity is a path rule, not an intent detector. It also depends on the repository using one of the detected directory names.
  • diff.syntax is Python-only. It parses changed .py files. There is no TypeScript, Go, Rust, or Java syntax check in the default contract.
  • Workspace mode weakens diff checks. --workspace reads current files, so diff.max_lines and diff.public_api are effectively no-ops. --git-preimage and the hook restore a baseline when HEAD exists.
  • --run-tests executes repository code. It runs in a temporary copy, not a sandbox. Audit only repositories you trust.
  • Test evidence inference is heuristic. It recognizes common runners and structured outcomes; ambiguous output stays unset and escalates. It is not proof that the full suite ran.
  • The field corpus is one user's history with no human labels. The 162-session numbers are calibration signals, not a prevalence study. Zero confirmed tampering in the five strongest candidates is not zero in the population.
  • This is not a security boundary. It is a review aid and an acceptance gate. It does not sandbox the agent, enforce filesystem permissions, or prove that no other process changed the tree.
  • No model calls, no semantic understanding. The rules are deterministic. That is a feature for reproducibility and a limitation for intent.

9. Test evidence

I ran the suite against the 0.5.0 repository on 2026-11-24 with Python 3.12.13 and pytest 9.2.0:

python -m pytest -q
88 passed, 1 warning in 4.16s

The warning is an expected one from tests/test_jsonl.py: a directory loader intentionally skips an unreadable package.json and emits a RuntimeWarning.

The tests that carry the claims in this post:

  • tests/test_codex.py::CodexTranscriptTest::test_codex_patch_is_replayed_and_test_deletion_is_found — replays a delete patch, asserts artifacts, test evidence, and the tests.integrity finding.
  • tests/test_codex.py::CodexTranscriptTest::test_codex_patch_update_reconstructs_the_file — asserts the reconstructed content after an update hunk.
  • tests/test_codex.py::CodexTranscriptTest::test_codex_patch_cannot_escape_the_baseline — asserts a ../ path produces no artifacts and no escaped file.
  • tests/test_codex.py::CodexTranscriptTest::test_find_latest_session_matches_recorded_workspace — asserts mtime ordering and workspace matching.
  • tests/test_codex.py::CodexTranscriptTest::test_find_latest_claude_session_from_workspace_subdirectory — asserts ancestor matching from a nested directory.
  • tests/test_codex.py::CodexTranscriptTest::test_cli_latest_codex — end-to-end --latest codex, exit code 1, and the tests.integrity finding.
  • tests/test_hook.py::ClaudeCodeHookTest::test_git_working_tree_changes_are_audited — simulates a Bash-only test edit and asserts the hook finds it through the git working tree.
  • tests/test_hook.py::ClaudeCodeHookTest::test_block_mode, test_warn_dedupes_same_finding, test_stop_hook_active_prevents_loop, test_missing_transcript_fails_open — the hook's failure and loop behavior.

A synthetic end-to-end run of --latest codex, built to the same record shape as the Codex tests, produced:

latest codex session: /tmp/.../sessions/2026/11/24/session.jsonl
Assaystone audit
baseline: .
traces: 1 (0 clean, 1 with findings)

demo-codex  changed: tests/test_calc.py
  REVIEW   evidence.claims          agent claims tests pass but no test evidence was recorded
  HIGH     tests.integrity          tests/test_calc.py (deleted)
  MEDIUM   diff.public_api          tests/test_calc.py: public module deleted

summary: 0 critical, 2 high, 1 medium, 0 low

suggested contract: rerun with --write-contract .assaystone/contract.json

That output is a useful example of the design. The deleted test is a high-severity path finding. The success claim escalates because the synthetic session never ran a test command. The public-API rule also fires on the deleted test module, which is the proxy noise described above. All three are deterministic and reviewable; none is a claim about intent.

What is not verified

  • Real current Codex and Claude Code binaries. The fixtures are synthetic, even though they mirror the current record shapes.
  • False-positive and false-negative rates on a labeled, multi-user corpus.
  • Non-Python syntax, binary patches, and tool-name or argument-shape drift.
  • Windows path behavior and very large sessions.
  • Sandboxing. --run-tests executes repository code in a temporary copy, not a sandbox.

10. Run it

# install and audit the newest session for this workspace
pip install assaystone==0.5.0
assaystone audit --latest claude-code
assaystone audit --latest codex

# audit an explicit transcript
assaystone audit ~/.claude/projects/<project>/<session>.jsonl --baseline .

# prefer git truth when the changes are real
assaystone audit session.jsonl --baseline . --git-repo .

# restore a pre-session baseline for diff checks
assaystone audit session.jsonl --baseline . --git-preimage \
  --write-contract .assaystone/contract.json

# machine-readable output for CI
assaystone audit --latest claude-code --json
assaystone audit agent-transcripts/ --baseline . \
  --sarif results.sarif --junit results.xml --fail-on high

# run the audit after every Claude Code turn
assaystone hook install claude-code --mode warn
assaystone hook install claude-code --mode block

The contract model is the part worth keeping. Every check returns one of three outcomes: pass when independent evidence supports the property, fail when evidence contradicts it, and escalate when the available checks cannot decide safely. The audit is the entry point; the same contract can gate CI and runtime.

The honest positioning is not “Assaystone detects cheating.” It is: Assaystone makes the acceptance boundary explicit, testable, and reviewable. A path rule can tell you that test files changed. It cannot tell you whether the agent protected the product or protected itself. Knowing the difference is the whole job.
