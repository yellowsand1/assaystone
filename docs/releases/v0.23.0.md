# v0.23.0 — Which checks earn their keep

Released 2026-11-25.

The trail has been recording, for every decision, which oracle ran and what it
said. This release reads it: the empirical half of "price the verification".

## Highlights

- **`capability utility`.** Per-oracle runs, passes, failures, escalations, and
  last outcome; the stage mix; checks that are required but never recorded;
  checks that have never observed a failure; oracles declared but unused.

  ```text
  oracle     runs  pass  fail  esc  required  last
  compile       6     5     1    0       yes  pass
  lint          6     6     0    0       yes  pass

  never observed a failure: lint
    this is a fact, not a verdict: the check may be doing its job, or it may be
    unable to fail
  ```

- **The honesty rule carries over.** Recall is not resistance; "never failed" is
  not "works". An oracle you have never seen reject anything is untested, not
  proven, and the report says so instead of ranking it.

- **A broken trail is not read** (exit `2`); a missing trail says so rather than
  reporting zeros.

## Evidence

- 594 tests, lint clean, CI on Python 3.10–3.13, seven required checks.
- Run end to end on a six-decision trail: one check failed once, one never did,
  one was declared and unused — all three reported correctly.

## Known limits

- The report covers one capability and one trail. A team view across
  capabilities is still `capability list`.
- It reports observations, not judgements: it cannot tell a vacuous check from a
  good one, only that it has never rejected anything.
- The semantic gap, canary traffic control, and the sandbox are unchanged.
