# v0.25.0 — Read the standard out of the repository, and check the change

Released 2026-11-25.

The two gaps I kept calling "the expert writes it" or "someone must specify it"
were mostly avoidable. This release derives the standard from the repository, and
adds the check that answers "do the tests cover the change".

## Highlights

- **`capability init` proposes the checks the repository implies**:

  | what is there | what is proposed |
  |---|---|
  | `src/main/java` + a Maven module | the public API is unchanged (`javap` vs baseline) |
  | a test tree | no test deleted or weakened (`tests.integrity`) |
  | `.github/workflows` | the CI configuration is unchanged (`diff.ci_surface`) |
  | a dependency manifest | the dependency set is unchanged |
  | `db/migration` | every new migration declares a down path |
  | a Python test suite | **the change is covered by the tests** (`mutation`) |

  Each proposal says why it applies; the payload scripts it needs are written to
  `.assaystone/checks/`.

- **`capability propose`** does the same against an existing manifest, so the
  standard grows as the repository does. `--apply` adds the criteria, writes the
  helpers, refuses an invalid result, and says the owner approval is now stale.

- **`mutation` oracle (twelfth primitive).** Inject one plausible defect at a time
  into the **added lines**, run the suite, require most mutants to be killed.
  Test files are never mutated; a red baseline escalates; survivors are named.
  This is the deterministic answer to "tests pass, so the behaviour must be fine",
  which was the largest remaining hole.

- **Canary, pinned by a test.** A canary is `shadow` across two endpoints with
  `ignore` and `tolerance`, or an `http` threshold for an aggregated metric. No
  new primitive was needed; the pattern was undocumented.

- **`command` gains `unknown_exit`**: an exit code meaning *could not decide*
  escalates instead of failing. The API check uses it when the baseline will not
  build.

## Evidence

- 625 tests, lint clean, CI on Python 3.10–3.13, seven required checks.
- Mutation check, run on a pricing fixture: an untested helper → `fail`, score
  0%, survivors named in that function; the same change with a test → `pass`,
  score 100%. The first version mutated the test files and scored 40% on a
  covered change — that bug is why tests are excluded.
- `capability propose` on a repo with tests, CI, and a `pom.xml`: three
  proposals, applied, then "nothing new to propose".

## Known limits

- `mutation` is Python-only, and an equivalent mutant can survive. It measures
  coverage of a change, not its correctness.
- Proposals are structural: they infer what the repository contains, not what the
  business means.
- Canary compares one measurement per run, not a distribution.
- The semantic and organisational limits that remain are stated in
  `docs/plane.md`.
