# v0.6.0 — The acceptance plane

Released 2026-11-25.

0.6.0 is the first release where Assaystone answers a deployment question, not
only an artifact question: *should this agent capability move forward, with what
evidence, and can someone else check the decision later?*

## Highlights

- **Capability manifests and lifecycle gates.** A manifest declares the owner,
  systems, data classes, irreversible actions, typed criteria, oracle bindings,
  and what `shadow`, `canary`, and `production` require. A gate that cannot
  decide exits `2`, never `0`.
- **Nine generic oracle primitives.** `command`, `file`, `git`, `human`, `http`,
  `sql`, `shadow`, `transcript`, and `verifier`. The core does not know Maven,
  Flyway, MySQL, or pricing; those are payloads.
- **Oracle registry.** Shared definitions live in a versioned `oracles.json`.
  A manifest pins a version, a ref cannot override the payload, and every oracle
  carries a fingerprint that reaches the audit trail.
- **Assurance gap, twice.** Each stage reports declared criteria it does not
  gate; `capability validate --strict` catches a critical criterion that no
  stage gates at all.
- **Checked rollback.** `rollback_required` must name a rollback oracle, and the
  gate runs it. A policy that asserts rollback without evidence is invalid.
- **Hash-chained trail.** `gate --audit` records actor, stage, outcome,
  per-oracle evidence digests, missing oracles, and the manifest digest.
  `trail verify --expect HASH` detects edits, gaps, and a truncated tail.
- **Verifier checks as oracles.** `tests.integrity`, `diff.forbidden_paths`, and
  other artifact-trusting checks can decide a stage over the working-tree diff,
  with their claim, blind spots, and independence attached.
- **Session evidence.** The `transcript` oracle runs the audit over an agent
  session. Findings inherit the provenance rules, so a failure that rests on
  agent testimony escalates instead of deciding.
- **Canary metrics.** `http` supports `lte`, `gte`, `lt`, and `gt` on a JSON
  path, so an error rate or a p95 latency can be a required stage check.
- **Onboarding.** `capability init` drafts a manifest from a repository;
  `assaystone demo plane` shows pass, fail, approval, and a tampered trail in
  one screen.

## Evidence in this release

- 409 tests, lint clean, CI on Python 3.10–3.13, including a wheel-install demo.
- A real Maven module: compiled and gated on a feature branch; the same gate
  failed on `develop` at the branch oracle.
- MySQL 8.0.31: the read-only session was verified through the adapter, scalar,
  row, and CTE expectations passed, and writes were rejected before a
  connection. This found and fixed a `DECIMAL` comparison bug.
- A real Claude Code session: 12 artifacts through the transcript oracle and one
  unsupported-language escalation. The same run exposed a false-clean on a
  zero-artifact session, now an escalation.

## Known limits

- The trail proves integrity, not authenticity. Anchor the head hash externally;
  tail truncation is otherwise invisible.
- An unsigned `approvals.json` is a file. Sign it with `hmac_env`, or keep it
  outside the agent's write path.
- Unsupported source languages escalate through `diff.language_coverage`. The
  plane's answer is compile, shadow, or SQL evidence, not a language-specific
  check.
- The Goodhart suite still measures 0% resistance for the semantic family
  (85% overall on its 13 defective cases). The plane does not change that.
- A manifest you run is trusted. The plane is not a sandbox.

## Upgrade

```bash
pip install --upgrade assaystone==0.6.0
```

The verifier ABI and contract format are unchanged; existing contracts keep
working. New commands: `capability init`, `capability validate --strict`,
`gate --audit`, `trail verify`. For the GitHub Action, pin
`yellowsand1/assaystone@v0.6.0`.
