# v0.14.0 — Receipts a third party can verify

Released 2026-11-25.

0.13.1 closed the incident stage. 0.14.0 removes the shared secret from the
receipt: the signer keeps a private key, the verifier holds only the public key.

## Highlights

- **Ed25519 receipts.** With the optional `cryptography` extra
  (`pip install "assaystone[crypto]"`):
  - `key generate --private owner.key --public owner.pub` writes a PKCS#8
    private key at `0600` and a public key;
  - `gate --receipt --receipt-key-file owner.key` signs with Ed25519;
  - `receipt verify --public-key owner.pub --outcome pass` verifies without the
    ability to sign.
- **Scheme selection is explicit.** The signature prefix (`hmac-sha256:` or
  `ed25519:`) selects the path; an Ed25519 receipt without a public key is
  invalid, not silently downgraded.
- **Optional dependency.** HMAC remains the default; importing Assaystone does
  not need `cryptography`, and the core stays dependency-free. The dev extra
  includes it so CI exercises Ed25519.
- **The Action** gains `receipt-key-file`.

## Evidence

- 483 tests, lint clean, CI on Python 3.10–3.13.
- The Ed25519 tests run in the quality job (`.[dev]` includes `cryptography`);
  they skip only when the extra is absent.
- Receipts still bind the commit, manifest digest, trail head, and every oracle
  digest; the change is the key model, not the coverage.

## Known limits

- Key rotation and revocation are not implemented; there is no identity system
  behind a key. The docs say so.
- Owner approvals and waivers still use HMAC. Extending the same Ed25519 model to
  them is the next step; until then CI needs the owner's shared key to verify
  them.
- The HMAC path remains for single-team pipelines.
- The semantic gap, the fixture SQL domain, and the working-tree rollback limit
  remain as stated.

## Upgrade

```bash
pip install --upgrade assaystone==0.14.0
# optional:
pip install "assaystone[crypto]==0.14.0"
```

For the GitHub Action, pin `yellowsand1/assaystone@v0.14.0`.
